1. The Big Picture: What is Docker & Why Does It Matter?

Before containerization, the most common frustration in software engineering was the classic: "It works on my machine, but crashes in production!"

  • Your laptop had Java 17.0.8, but production had Java 11.
  • Production was missing an environment variable or system library.
  • Node.js version mismatches caused client bundle errors.
🚢 The Standard Shipping Container Analogy:
Before 1956, shipping cargo was chaotic: bananas, cars, barrels, and sacks all had different shapes. Cranes broke, ships couldn't dock at every port, and loading took weeks.

The invention of the Standard Intermodal Shipping Container changed global trade forever: regardless of what is packed inside, every container has standard dimensions and fits onto any cargo ship, freight train, or flatbed truck in the world.

Docker is the shipping container of software: It packages your code, runtime (JRE/Node), libraries, and OS settings into a standardized, isolated container that executes identically on Windows, Linux, macOS, AWS, or Render!

2. Multi-Stage Builds: The Senior Engineer Secret

A common beginner mistake is writing a single-stage Dockerfile that compiles code and runs it in the same container. This results in bloated, insecure 800MB+ images containing compilers and build tools that shouldn't exist in production.

How Our Backend Multi-Stage Build Works:

STAGE 1: BUILDER (maven:3.9.6-eclipse-temurin-17-alpine) ~800MB ├── Copies pom.xml & downloads dependencies ├── Copies Java source code └── Compiles & packages: flashpass-engine.jar │ ▼ [DISCARDS THE ENTIRE COMPILER, MAVEN & SOURCE CODE!] │ STAGE 2: RUNTIME (eclipse-temurin:17-jre-alpine) ~150MB ├── Ultra-lightweight Alpine Linux kernel + JRE (No Maven, No javac) ├── Creates non-root system user 'flashpass' (Security Best Practice) ├── Copies ONLY the compiled .jar file from Stage 1: │ COPY --from=builder /app/target/*.jar app.jar └── Result: 80% SMALLER IMAGE SIZE & ZERO BUILD TOOL VULNERABILITIES!

3. Docker Layer Caching (Why Order of Commands Matters!)

Look closely at how we structured our Backend and Frontend Dockerfiles:

# 1. Copy dependencies FIRST COPY pom.xml . RUN mvn dependency:go-offline -B # 2. Copy source code SECOND COPY src ./src RUN mvn clean package -DskipTests

Why is this an interview favorite?

  • Docker caches each line as an immutable image layer.
  • If you copied source code first (COPY . .), every time you changed a single line of Java or React code, Docker's cache would be invalidated, forcing a slow 5-minute download of all Maven/npm dependencies!
  • By copying pom.xml / package.json first, Docker reuses the cached dependencies in under 2 seconds unless your dependencies actually change!

4. Frontend Production Architecture: Why Nginx Over Node.js?

In development, we ran npm run dev using Vite's local Node.js development server. In production, we never run Node.js to serve a React SPA!

STAGE 1: Node.js 20 Builder ├── Compiles React JSX into raw, static HTML, CSS, and JS bundles inside /dist │ ▼ [Node.js (~450MB) is completely discarded!] │ STAGE 2: Nginx Web Server (~25MB) ├── Serves static files directly from RAM using C-based event-driven architecture ├── Configures Gzip compression (slashes bundle transfer size by 70%) └── Implements SPA Routing: try_files $uri $uri/ /index.html;
⚡ Why Nginx?
React after compilation is just flat static files (HTML, CSS, JS). Keeping a heavy Node.js server running in production just to serve static text files is like hiring a semi-truck to deliver an envelope. Nginx is an ultra-fast, lightweight C-based web server specifically engineered for maximum throughput.

5. Full-Stack Orchestration: `docker-compose.yml`

Rather than manually running separate docker build and docker run commands with lengthy port and environment variable flags, Docker Compose orchestrates both microservices:

version: '3.8' services: flashpass-backend: build: ./flashpass-engine ports: ["8080:8080"] environment: - SPRING_DATASOURCE_URL=... - SPRING_DATA_REDIS_HOST=... flashpass-frontend: build: ./flashpass-ui ports: ["80:80"] depends_on: [flashpass-backend]

A single command: docker compose up --build builds both containers, links their internal network, and exposes the frontend on port 80 and backend on port 8080!

6. Master Interview Cross-Questions & Model Answers

Q1. What is a Multi-Stage Docker build, and why did you use it?
How to answer:
"A multi-stage build separates the build environment from the runtime environment using multiple FROM directives in a single Dockerfile. In Stage 1, we use full build images (Maven JDK or Node.js) to compile and package artifacts. In Stage 2, we copy only the compiled binary (JAR or Nginx dist folder) into a minimal Alpine Linux runtime image.

This reduced our backend image size from ~850MB to ~160MB (and frontend from ~500MB to ~25MB), drastically cut container deployment pull times, and minimized the security attack surface by excluding compilers and build tools from production."
Q2. Why did you create a non-root user in your backend Dockerfile? (Container Security)
How to answer:
"By default, processes inside a Docker container execute as the root user. If an attacker discovers a Remote Code Execution (RCE) vulnerability in an application library, they obtain root privileges inside the container, potentially allowing a container breakout to compromise the host kernel. Adding USER flashpass enforces the Principle of Least Privilege, preventing unauthorized host manipulation."
Q3. What is the purpose of .dockerignore?
How to answer:
"When Docker builds an image, the Docker CLI first copies the current directory into the Docker Daemon (the build context). .dockerignore prevents large or sensitive directories (such as local target/, node_modules/, .git/, and IDE configuration files) from being sent to the daemon. This dramatically accelerates build speeds and prevents local build artifacts or secrets from leaking into the container."
Q4. In Java containers, why do you include -XX:+UseContainerSupport and -XX:MaxRAMPercentage?
How to answer:
"Historically, the JVM read the host machine's total physical memory rather than the container's cgroup memory limits. In a container restricted to 512MB RAM on a 16GB host, an unconstrained JVM would allocate default heap based on 16GB, causing the Linux Out-Of-Memory (OOM) killer to instantly terminate the container.

-XX:+UseContainerSupport (default in Java 17+) and -XX:MaxRAMPercentage=75.0 instruct the JVM to size its heap strictly against the container's allocated memory boundary."
Q5. Why do we need try_files $uri $uri/ /index.html in Nginx for React?
How to answer:
"React is a Single Page Application (SPA) utilizing client-side routing. When a user directly visits or refreshes a nested URL like /seats/confirm, the browser requests that physical file from Nginx. Because only index.html physically exists on disk, Nginx would return a 404 Not Found error. try_files $uri $uri/ /index.html; tells Nginx: if the requested file doesn't exist, fallback to index.html so React's client router can parse the URL and render the correct view."
