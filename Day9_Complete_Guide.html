🔧 2. Every Single Code Change Made in Day 9 & The "Whys"

Change 1: Dynamic Port Binding in Spring Boot

File: flashpass-engine/src/main/resources/application.properties

# BEFORE (Hardcoded port):
server.port=8080

# AFTER (12-Factor App Dynamic Cloud Port Binding):
server.port=${PORT:8080}

The Why: In local development, Spring Boot listens on port 8080. But cloud PaaS providers (Render, Heroku, Railway, AWS ECS) assign dynamic listening ports at container launch time by injecting an environment variable (e.g. PORT=10000). If your app hardcodes 8080, the cloud container crashes with a port binding mismatch. ${PORT:8080} uses the cloud's PORT variable when running in production, but seamlessly falls back to 8080 when running locally!

Change 2: Production SSL WebSocket Negotiation & Mixed-Content Protection

File: flashpass-ui/src/App.jsx

// Dynamic REST API Base URL
const API_BASE_URL = import.meta.env.VITE_API_BASE_URL || 'http://localhost:8080/api';

// Intelligent WebSocket Broker URL Resolution
const getWsBrokerUrl = () => {
  if (import.meta.env.VITE_WS_BROKER_URL) {
    return import.meta.env.VITE_WS_BROKER_URL;
  }
  if (import.meta.env.VITE_API_BASE_URL) {
    const rawUrl = import.meta.env.VITE_API_BASE_URL.replace(/\/api\/?$/, '');
    if (rawUrl.startsWith('https://')) {
      return rawUrl.replace('https://', 'wss://') + '/ws-flashpass';
    } else if (rawUrl.startsWith('http://')) {
      return rawUrl.replace('http://', 'ws://') + '/ws-flashpass';
    }
  }
  return 'ws://localhost:8080/ws-flashpass';
};

const WS_BROKER_URL = getWsBrokerUrl();

The Why:

  • Mixed Content Security Policy: When Vercel serves the React SPA over https://, modern browsers (Chrome, Edge, Safari) strictly BLOCK unencrypted HTTP requests (http://) and unencrypted WebSockets (ws://).
  • Our logic automatically inspects the API URL: if it detects https://, it seamlessly upgrades the WebSocket protocol to wss:// (WebSocket Secure over TLS), preventing browser security exceptions!
  • If running on your local machine, it safely defaults back to ws://localhost:8080/ws-flashpass.

Change 3: Environment Template (`flashpass-ui/.env.example`)

# Production Backend REST API URL (Render)

🎯 5. Senior Engineering Interview Defensibility (Verbatim Answers)

Q1: Why did you separate frontend hosting (Vercel) from backend hosting (Render) instead of bundling React into Spring Boot's static folder?
Verbatim Answer:
"Bundling static React assets into a Spring Boot JAR is an anti-pattern that couples two entirely different scaling profiles. By hosting the frontend on Vercel's global Edge CDN, static UI assets (HTML, CSS, JS) are cached at points of presence worldwide and served with sub-10ms latency at zero server compute cost.

The backend container on Render runs strictly as an API and WebSocket gateway. This decouples our architecture: UI traffic spikes never degrade database connection pools, and backend deployments never disrupt frontend availability."
Q2: How do WebSockets work in production behind cloud proxies and TLS/SSL?
Verbatim Answer:
"In production, WebSockets begin with an HTTP/1.1 handshake initiated over HTTPS. The browser transmits Upgrade: websocket and Connection: Upgrade headers. The cloud reverse proxy (Render) terminates the TLS encryption, verifies the handshake, and upgrades the underlying TCP connection to a persistent, bidirectional WebSocket channel.

Because our frontend dynamically detects HTTPS and requests wss:// (WebSocket Secure), the connection satisfies browser Mixed-Content security policies while maintaining sub-30ms real-time event broadcasting."
Q3: How do you handle cold starts on free-tier cloud containers like Render?
Verbatim Answer:
"Render free-tier instances spin down to 0 replicas after 15 minutes of inactivity to conserve resources. We engineered a two-tier solution:
1. Frontend UX: Our React client displays an interactive glowing HUD spinner ('Connecting to FlashPass Distributed Cloud Engine...') while waiting for the backend container to wake up.
2. Uptime Keep-Alive: In production demo scenarios, we configure a lightweight external cron ping (e.g., Cron-job.org or UptimeRobot) targeting the lightweight /api/events endpoint every 14 minutes, keeping the container permanently warm 24/7."
Q4: Why did you configure server.port=${PORT:8080} in application.properties?
Verbatim Answer:
"This implements Factor III of the Twelve-Factor App methodology: Config in the Environment. Container runtimes and cloud platforms dynamically bind applications to ephemeral ports assigned by the host operating system, injecting that value into the PORT environment variable. By declaring server.port=${PORT:8080}, Spring Boot dynamically adapts to the host container environment while maintaining a local fallback of 8080."
Q5: How does your monorepo structure support CI/CD without causing unnecessary rebuilds?
Verbatim Answer:
"Our monorepo isolates domains into flashpass-engine and flashpass-ui. Both Render and Vercel support Root Directory path targeting. When a Git commit modifies only frontend components in flashpass-ui, Vercel initiates an edge build while Render ignores the commit, preventing wasteful container rebuilds. Conversely, root orchestration via docker-compose.yml enables any developer to clone a single repository and spin up the complete distributed topology locally in one command."
