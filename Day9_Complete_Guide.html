🏛️ 1. Why a Monorepo? Clean GitHub & Unified Architecture

Instead of scattering the project across separate repositories on GitHub (flashpass-engine and flashpass-ui), we unified everything into a single, cohesive repository: flashpass.

💡 The Non-Coder Analogy: The Single Blueprint Binder

Imagine constructing a skyscraper. You have architectural blueprints for the electrical grid (Backend) and interior design layouts for the lobby (Frontend). If you store them in two separate offices across town (Polyrepo), nobody can see the whole building at once. A Monorepo is binding both sets of blueprints into a single master engineering folio. Anyone reviewing your work sees the entire stadium system in one clean glance.

🔧 3. Code Modifications & The Engineering "Whys"

1. Dynamic Cloud Port Binding (`application.properties`)

# BEFORE (Hardcoded local port)
server.port=8080

# AFTER (12-Factor App cloud-native dynamic port)
server.port=${PORT:8080}

The Why: Cloud PaaS providers like Render, Railway, and Heroku assign a dynamic port to each web service at runtime by injecting an environment variable (PORT=10000). If an application hardcodes 8080, the cloud container crashes with a port binding failure. ${PORT:8080} instructs Spring Boot: "Use the environment variable PORT if present; otherwise, fall back to 8080 for local development."

2. Dynamic WebSocket Protocol Upgrade (`App.jsx`)

const API_BASE_URL = import.meta.env.VITE_API_BASE_URL || 'http://localhost:8080/api';

// Native WebSocket endpoint supporting both local dev and production SSL (wss://)
const getWsBrokerUrl = () => {
  if (import.meta.env.VITE_WS_BROKER_URL) {
    return import.meta.env.VITE_WS_BROKER_URL;
  }
  if (import.meta.env.VITE_API_BASE_URL) {
    const rawUrl = import.meta.env.VITE_API_BASE_URL.replace(/\/api\/?$/, '');
    if (rawUrl.startsWith('https://')) {
      return rawUrl.replace('https://', 'wss://') + '/ws-flashpass';
    } else if (rawUrl.startsWith('http://')) {
      return rawUrl.replace('http://', 'ws://') + '/ws-flashpass';
    }
  }
  return 'ws://localhost:8080/ws-flashpass';
};

const WS_BROKER_URL = getWsBrokerUrl();

The Why: When your React app is served over HTTPS on Vercel, web browsers enforce Mixed Content Security. Browsers will automatically block insecure http:// REST calls and insecure ws:// WebSockets. Our function intelligently detects https:// on the cloud API URL and automatically switches to wss:// (WebSocket Secure over TLS), while still defaulting to ws://localhost:8080 during local testing!

🚀 4. Step-by-Step Monorepo Cloud Deployment

Step A: Push Your Monorepo to GitHub

  1. Go to github.com/new and create a repository named: flashpass (Public, no template).
  2. In your terminal, run: 
    cd "D:\Eclipse Workspace for ProjectShowCase"
git remote add origin https://github.com/KiranKumarBehera/flashpass.git
git push -u origin main

Step B: Deploy Backend Container on Render

  1. Sign up / Log in to render.com with your GitHub account.
  2. Click New + → Web Service → Select your flashpass repository.
  3. Configure these exact settings:
    • Name: flashpass-engine
    • Root Directory: flashpass-engine ← (Crucial: Tells Render where Dockerfile lives)
    • Runtime: Docker
    • Instance Type: Free
    • Health Check Path: /api/events
  4. Click Deploy Web Service. Render will build the Docker container and give you your live URL: https://flashpass-engine.onrender.com

Step C: Deploy Frontend SPA on Vercel

  1. Sign up / Log in to vercel.com with your GitHub account.
  2. Click Add New... → Project → Import flashpass.
  3. Configure:
    • Root Directory: Click Edit and select flashpass-ui.
    • Framework Preset: Vite (Auto-detected).
    • Environment Variables:
      Name: VITE_API_BASE_URL
      Value: https://flashpass-engine.onrender.com/api (Your Render backend URL)
  4. Click Deploy. Vercel deploys your frontend within 30 seconds to: https://flashpass-ui.vercel.app

🎯 5. Senior Engineering Interview Defensibility

Q1: Why did you deploy frontend and backend to separate cloud platforms (Vercel + Render) instead of bundling everything into one Spring Boot JAR?
Verbatim Answer: "Bundling static React assets into Spring Boot's src/main/resources/static violates the Single Responsibility Principle and degrades user experience. By deploying the frontend to Vercel's Edge CDN, static assets (HTML/CSS/JS) are served with sub-10ms latency from edge caches geographically closest to the user. Meanwhile, the Render container runs solely as an API and WebSocket gateway. This decouples scaling: static UI reads scale infinitely at zero server cost, while Java compute resources are reserved exclusively for transactional database and cache operations."
Q2: How do WebSockets work in production behind cloud proxies and TLS/SSL?
Verbatim Answer: "In production, client-server communication starts with an HTTPS handshake. The client sends an HTTP GET request containing Upgrade: websocket and Connection: Upgrade headers. The cloud reverse proxy (Render/Vercel) terminates the SSL encryption (converting wss:// to plaintext ws:// internally) and delegates the connection to Spring Boot's Tomcat WebSocket endpoint at /ws-flashpass. Because our frontend dynamically constructs the wss:// URI, browser Mixed-Content policies are satisfied."
Q3: How does your monorepo structure support independent continuous deployment (CI/CD)?
Verbatim Answer: "Our monorepo cleanly isolates domains into /flashpass-engine and /flashpass-ui. Both Render and Vercel support subdirectory root path targeting. When a commit changes only frontend files, Vercel triggers a build while Render remains untouched, avoiding unnecessary backend rebuilds. Furthermore, root orchestration via docker-compose.yml allows any engineer to clone a single repository and spin up the complete end-to-end distributed system locally in one command."
Q4: Free tier cloud services (like Render) sleep after 15 minutes of inactivity. How do you mitigate cold starts?
Verbatim Answer: "Render's free tier spins down idle containers after 15 minutes to conserve compute. To handle this in production showcase environments, I implemented two strategies: first, the frontend displays an interactive glowing HUD loader ('Connecting to FlashPass Distributed Cloud Engine...') during initial cold-start wakeups (~30s). Second, we can configure a lightweight free uptime ping (e.g., Cron-job.org or UptimeRobot) calling the /api/events health check every 14 minutes to keep the container permanently warm 24/7."
