🏛️ 1. The Monorepo Architecture & Clean Git Workspace Isolation

In production engineering, choosing repository topology is a foundational architectural decision. Initially, we considered two separate repositories (flashpass-engine and flashpass-ui). However, we chose a Unified GitHub Monorepo (github.com/KiranKumarBehera/flashpass).

💡 The Non-Coder Analogy: The Single Architectural Master Blueprint
Imagine constructing a high-tech smart stadium. You have structural blueprints for high-voltage power grids, high-speed fiber, and hydraulic gates (the Backend), and you have blueprints for ticketing kiosks, VIP suites, and turnstiles (the Frontend).

If you store them in two different folders in two separate buildings, no inspector or client can grasp the complete synchronized system in a single visit. A Monorepo binds both blueprints into one elegant master folio. Any hiring manager or interviewer visiting Kiran's GitHub sees the entire distributed system in a single glance.

Eliminating Workspace Pollution: Strict .gitignore Strategy

🛡️ How We Guaranteed Zero Pollution:

☁️ 2. Render Cloud Backend Deployment: Docker, Dynamic Ports & SSL

The backend is deployed as a Render Docker Web Service in Frankfurt/Oregon. Render pulls our GitHub repository, navigates to the flashpass-engine root directory, and executes our multi-stage Docker build.

12-Factor App Dynamic Cloud Port Binding

In local development, Spring Boot binds to static port 8080. However, cloud PaaS runtimes dynamically assign arbitrary listener ports (e.g. PORT=10000) to prevent internal port collisions across host containers.

Setting Local Development Cloud Production (Render) Why Dynamic Resolution Matters
Listening Port 8080 Injected ${PORT} (e.g. 10000) server.port=${PORT:8080} allows seamless execution locally while adhering to cloud orchestration without code modification.
Database SSL SSL Mode optional sslmode=require Neon PostgreSQL enforces encrypted TLS transport over port 5432.
Redis Protocol redis:// (plaintext) rediss:// (TLS Secure) Upstash Redis enforces TLS on port 6379; regular redis:// connections will be rejected.

⚡ 3. Vercel Edge Frontend Deployment: Vite, Mixed-Content & WSS

The frontend SPA is hosted on Vercel's Anycast Edge CDN. Rather than serving static React assets through Spring Boot's JVM container, Vercel caches assets worldwide with sub-10ms time-to-first-byte (TTFB).

Preventing Mixed-Content Browser Blockers: Intelligent WSS Upgrade

🚨 The Mixed-Content Trap:
When a user accesses https://flashpass-three.vercel.app over HTTPS, modern web browsers enforce strict Content Security Policy (CSP). Any unencrypted WebSocket connection attempt (ws://) or HTTP call (http://) is blocked instantly by the browser engine with a console security violation!

We solved this declaratively in src/App.jsx with automatic protocol negotiation:

// Dynamic WebSocket Protocol Negotiation
const getWsBrokerUrl = () => {
  if (import.meta.env.VITE_WS_BROKER_URL) {
    return import.meta.env.VITE_WS_BROKER_URL;
  }
  if (import.meta.env.VITE_API_BASE_URL) {
    const rawUrl = import.meta.env.VITE_API_BASE_URL.replace(/\/api\/?$/, '');
    // If frontend is HTTPS, seamlessly upgrade WebSocket to WSS (Secure TLS)
    if (rawUrl.startsWith('https://')) {
      return rawUrl.replace('https://', 'wss://') + '/ws-flashpass';
    } else if (rawUrl.startsWith('http://')) {
      return rawUrl.replace('http://', 'ws://') + '/ws-flashpass';
    }
  }
  return 'ws://localhost:8080/ws-flashpass';
};

Vercel SPA Client-Side Routing: vercel.json

{
  "rewrites": [
    { "source": "/(.*)", "destination": "/index.html" }
  ]
}

Without this configuration, if an interviewer refreshes a deep URL on Vercel, the edge server returns HTTP 404 because no physical file exists for that path. The rewrite rule instructs Vercel to redirect all incoming routes back to /index.html, allowing React 19 client-side routing to handle navigation flawlessly.

3. Dynamic Inventory Generation in SeatService.java

Location: flashpass-engine/src/main/java/com/kiran/flashpassengine/service/SeatService.java

@Transactional
public Event createEventWithSeats(Event event, String rowsStr, int seatsPerRow) {
    Event savedEvent = eventRepository.save(event);
    String[] rows = rowsStr.split(",");
    List<Seat> generatedSeats = new ArrayList<>();

    for (String row : rows) {
        String trimmedRow = row.trim().toUpperCase();
        boolean isVip = trimmedRow.equals("A");
        double price = isVip 
            ? (event.getBasePriceVip() != null ? event.getBasePriceVip() : 5000.0)
            : (event.getBasePriceStd() != null ? event.getBasePriceStd() : 2500.0);

        for (int i = 1; i <= seatsPerRow; i++) {
            Seat seat = new Seat();
            seat.setEventId(savedEvent.getId());
            seat.setSeatNumber(trimmedRow + i);
            seat.setStatus(SeatStatus.AVAILABLE);
            seat.setPrice(price);
            generatedSeats.add(seat);
        }
    }
    seatRepository.saveAll(generatedSeats);
    evictSeatsCache(savedEvent.getId());
    return savedEvent;
}

The Why: Dynamically generates JPA entities with initial version = 0 in a single batch operation (saveAll), minimizing roundtrips to Neon PostgreSQL. Automatically purges Redis cache so fans immediately see the fresh stadium layout.

🎯 6. Senior & Staff Engineering Interview Defensibility (Verbatim Answers)

Q1: How do you prevent double-booking when 100,000 fans click the same Coldplay front-row seat simultaneously?
Verbatim Answer:
"We utilize JPA Optimistic Locking with a dedicated @Version column. When 100,000 concurrent requests attempt to lock Seat A1, all read version 0. The first transaction to reach the database executes UPDATE seats SET status='LOCKED', version=1 WHERE id=1 AND version=0. That update succeeds and increments the version to 1. The remaining 99,999 transactions fail because their WHERE clause version=0 no longer matches. Hibernate throws an OptimisticLockingFailureException, which our global @RestControllerAdvice translates into HTTP 409 Conflict in sub-30ms. We avoid pessimistic database row locks, preventing thread starvation and connection pool exhaustion."
Q2: Why did you host the frontend on Vercel and backend on Render instead of serving everything from one Spring Boot JAR?
Verbatim Answer:
"Bundling static SPA assets into a Spring Boot JAR couples two completely distinct scaling and caching topologies. React assets (HTML, CSS, JS) are immutable static files that belong at Vercel's global Anycast Edge CDN, where they are served with sub-10ms latency worldwide at zero server compute cost. Meanwhile, our Spring Boot backend on Render scales compute independently based on CPU, JVM memory, and WebSocket connection concurrency. Furthermore, this separation enables independent CI/CD pipelines: UI redesigns deploy in 15 seconds without restarting the Java backend or dropping active WebSocket connections."
Q3: How do you handle abandoned shopping carts where a user locks a seat but never buys it?
Verbatim Answer:
"We enforce a dual-layer TTL lease architecture. On the client side, a 5-minute countdown timer visually informs the fan. On the backend, a background daemon annotated with @Scheduled(fixedRate = 10000) queries for seats where status = 'LOCKED' and lockedAt < NOW() - 5 minutes. Any expired seats are automatically reverted to AVAILABLE, cleared of holding user metadata, and a real-time STOMP event is broadcast to /topic/seats, instantly illuminating the seat green across all connected fan browsers."
Q4: What was the root cause of Cumulative Layout Shift (CLS) in your original UI, and how did you resolve it?
Verbatim Answer:
"Originally, toast alerts were rendered inline inside the main flexbox flow with margin-bottom: 24px. When an optimistic lock conflict triggered an error banner, it pushed the entire 50-row stadium layout down by 60 pixels, causing severe layout thrashing and poor Core Web Vitals. We resolved this by extracting toasts into fixed-position glassmorphism overlays (position: fixed; top: 24px; left: 50%; transform: translateX(-50%)). This decouples alerts from document flow, guaranteeing a rock-solid CLS score of 0.0."
Q5: How does your WebSocket architecture handle Mixed Content and cross-origin security in cloud production?
Verbatim Answer:
"When the frontend is served over HTTPS from Vercel, browser Content Security Policies block unencrypted ws:// traffic. Our frontend dynamically resolves the protocol: if the API protocol is HTTPS, it automatically negotiates wss:// (WebSocket Secure over TLS). On the backend, Spring's WebSocketConfig explicitly configures setAllowedOriginPatterns('*') to permit secure cross-domain WebSocket handshakes from Vercel while preserving sub-protocol integrity."
